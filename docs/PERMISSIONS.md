# 권한 및 데이터 관리 구조 (최종)

## 1. 역할별로 할 수 있는 일

| 기능 | 일반 방문자 (로그인 없음) | 일반 계정 (로그인했지만 관리자 아님) | 관리자 (나) |
| --- | :---: | :---: | :---: |
| 공연 목록, 상세, 캐스팅 스케줄, 할인·이벤트 보기 | O | O | O |
| 하트로 관심 공연·관심 배우 등록/해제 (내 브라우저에 저장) | O | O | O |
| 마이페이지: 관심 공연·관심 배우·내 일정 모아보기 | O | O | O |
| 관리자 화면(`/admin`) 접근 | X | X | O |
| 공연·배역·배우·회차 등록·수정·삭제, 포스터 업로드 | X | X | O |

- 관리자는 **내가 Supabase에서 직접 등록한 계정 한 개(또는 몇 개)**뿐이에요. 앱 안에서 관리자를 만들 방법은 없어요.
- 일반 방문자에게는 상단 막대에 "관리자 화면" 링크가 보이지 않아요. 다만 링크를 숨기는 건 편의일 뿐이고, 아래 세 겹의 잠금이 실제로 막아요.

## 2. 접근을 막는 세 겹의 잠금

| 겹 | 위치 | 하는 일 |
| --- | --- | --- |
| 1 | `middleware.ts` (서버, 페이지가 만들어지기 전) | `/admin` 아래 모든 주소를 확인해요. 로그인하지 않았으면 `/admin/login`, 로그인했지만 관리자가 아니면 `/`로 보내요. 확인 중 오류가 나도 열어 주지 않아요. |
| 2 | `app/admin/(protected)/layout.tsx` (서버) | 같은 확인을 한 번 더 해요. 첫 번째 잠금이 우회돼도 화면이 만들어지지 않아요. |
| 3 | Supabase RLS (DB) | **진짜 보안 경계예요.** 화면 잠금이 모두 뚫려도 관리자가 아니면 DB가 쓰기를 거부해요. |

`/admin/login`만 누구나 열 수 있어요(로그인 화면이니까요). 여기서 로그인해도 관리자로 등록된 계정이 아니면 바로 로그아웃돼요.

## 3. 데이터 관리 구조 (Supabase)

| 표 | 내용 | 읽기 | 쓰기 |
| --- | --- | --- | --- |
| `shows` | 공연 기본 정보, 포스터 | 누구나 | 관리자 |
| `roles` | 공연별 배역 | 누구나 | 관리자 |
| `cast_members` | 배역별 배우 | 누구나 | 관리자 |
| `sessions` | 회차(날짜·시간·커튼콜 데이·타임세일) | 누구나 | 관리자 |
| `session_cast` | 회차별 배역-배우 | 누구나 | 관리자 |
| `admins` | 관리자 계정 목록 | 아무도 API로 못 읽음 | 아무도 API로 못 씀 (SQL Editor에서만) |
| 저장소 `posters` | 포스터 이미지 | 누구나 (공개 주소) | 관리자 |

- **할인·이벤트 정보**는 별도 표가 없어요. 커튼콜·타임세일은 회차의 체크 값에서, 조기예매 안내는 `shows`의 안내 문구에서 계산해 보여줘요. 그래서 위 표들이 공개 읽기가 되면 이벤트 정보도 함께 공개 읽기예요.
- **하트(관심 공연·관심 배우)는 DB에 없어요.** 방문자 본인의 브라우저 저장소(`localStorage`, 키 `jjabkit-fav-v1`)에만 있고, 서버로 전송되지 않아요. 그래서 로그인 없이 쓸 수 있고, 다른 기기와는 공유되지 않아요.
- **관리자 판별**은 `public.is_admin()` 함수가 `admins` 표에 로그인한 계정이 있는지로 결정해요. 화면 코드가 값을 바꿔도 DB의 판단은 바뀌지 않아요.

## 4. 마이그레이션

1. `0001_init.sql` 하나로 충분해요: 표, 제약, RLS 정책, `is_admin()`, `save_session()`, 포스터 저장소, 그리고 맨 끝의 **권한 정리**(Supabase는 새 표에 `anon`·`authenticated` 권한을 기본으로 주므로 `admins` 표와 불필요한 쓰기 권한을 회수해요).
2. `0002_permissions.sql`은 **예전 버전의 0001만 실행해 둔 프로젝트**를 위한 패치예요. 같은 권한 정리만 담고 있고, 여러 번 실행해도 안전해요.
3. (선택) `seed.sql`: 샘플 공연 5개.

확인한 사실: Supabase와 같은 기본 권한 상태에서 권한 정리가 없으면 `admins` 표 읽기 차단 점검 2개가 실패해요. 지금의 `0001_init.sql` 하나만 실행한 새 데이터베이스에서는 25개 점검이 모두 통과했어요.

## 5. 관리자 등록과 점검

1. Authentication > Users에서 내 이메일·비밀번호로 사용자를 만들어요. 신규 가입(sign up)은 꺼 두세요.
2. SQL Editor에서 관리자로 등록해요.
   ```sql
   insert into public.admins (user_id)
   select id from auth.users where email = 'me@example.com';
   ```
3. `supabase/tests/rls_check.sql`을 SQL Editor에서 통째로 실행해요. 결과가 `ERROR: RLS 점검 결과`로 나오고 모든 줄이 `PASS`이면 정상이에요. (일부러 오류를 내서 점검용 데이터를 모두 되돌리기 때문에 데이터가 남지 않아요.)

## 6. 지켜야 할 것

- `service_role` 키는 앱, 환경변수, 저장소 어디에도 넣지 마세요. RLS를 우회하는 키예요.
- 공개 키(`NEXT_PUBLIC_SUPABASE_ANON_KEY`)는 브라우저에 노출되는 값이에요. 노출돼도 괜찮도록 RLS가 막고 있어요.
- 관리자를 추가하려면 가입시킨 뒤 `admins`에 SQL로 한 줄을 넣으면 되고, 빼려면 그 줄을 지우면 돼요.

## 7. 소식·백업 추가분 (0003)

- `notices` 표: 읽기 누구나, 추가·수정·삭제는 관리자만(RLS). 다른 표와 같은 방식이고, `truncate` 권한은 아무에게도 없어요. 공연이 삭제되면 소식에 연결된 공연 표시만 비워지고 소식은 남아요.
- `import_shows(jsonb, boolean)` 함수: `security invoker`라서 RLS가 그대로 적용돼요. 로그인하지 않은 방문자는 실행 권한이 없고, 로그인했지만 관리자가 아니면 시작하자마자 거부돼요. 한 번에 전부 성공하거나 전부 취소돼요.
- 백업 파일은 화면에서 먼저 검사하고, DB 함수도 날짜·시간·배역·배우를 다시 확인하며, 표의 제약 조건(장르·상태 값, 같은 날짜·시간 중복 금지, 글자 수 제한)이 마지막으로 막아요.
- 소식 본문은 HTML로 해석하지 않고 글자 그대로 그려요.
